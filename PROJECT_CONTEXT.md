# JScanner — project context

**Updated:** 2026-09-16
**Status:** working, first complete version

## Mandate

A mobile-first HTML5 app that takes document/receipt photos from a phone
gallery or camera, then straightens, crops and cleans them so the text is
readable by a human and by OCR.

Two decisions were confirmed with the user before building:

- **Fully client-side.** No server, no upload, no network. Works offline.
- **Clean image only.** No built-in OCR engine (no Tesseract.js). The output is
  tuned so that whatever OCR the user runs later works well.

This is unrelated to the quant-research work elsewhere in `C:\python\projects`;
it shares only the filesystem layout convention.

## Entry points

- `index.html` — the app. Open directly, or serve the folder.
- `js/00-utils.js` … `js/60-init.js` — classic scripts, load order matters
  (defined in `index.html`).
- `js/30-pipeline.js` holds the page model and the render pipeline; that is the
  file to read first.
- `js/50-ui.js` holds all state and interaction.
- `tests/fixtures/` holds the four reported photos, the only binary test inputs
  in the project; everything else is generated by the suites themselves.
  `tests/tmp/` is gitignored scratch.

The build number is `JS.VERSION` in `js/00-utils.js`, printed beside the name on
the home screen by `boot()`. The markup's span ships empty and `ui_flow` asserts
both that the screen matches the constant and that `index.html` holds no copy of
its own — a number typed into the HTML would pass a text comparison and go stale
in silence on the next bump.

**Current build: 1.5.0** — three changes. **A lit mode chip now takes its own mode
back off**: *Auto colour* and *B/W* remember the tone that was on the page the
instant before they were tapped, and a second tap restores it — so Receipt → *Auto
colour* → *Auto colour* ends in Receipt, with the crop, the straightening and the
sharpness untouched. **There are eight crop dots, not four** — a dot on each
corner and one on the middle of each side, the side dots moving that whole side in
one drag. And **Auto clean thresholds differently**: the local-*mean* rule
(Bradley–Roth) is replaced by a local mean *and* local contrast one (Sauvola), so a
window a thin stroke runs through is judged more leniently. On a faint, soft page
of print — 99 marks on the crisp original — whole/pieces went **71/28 → 81/18**,
and the new rule is a strict superset of the old one, so it can only add ink. The
output is **still one-bit black and white** in those modes, deliberately; see
**The threshold now reads contrast** below. Behind it: 1.4.0 merged the panel into
two labelled lines, moved Done up with the three auto buttons, put the pager in the
topbar and added pinch-zoom with a 2× auto-zoom onto a grabbed corner (page 49.0%
→ 74.4% of a 375×667 screen). 1.3.0 added the three-step **Sharpen** chip
(Greyscale is gone; Saturation −100 still reaches it), stopped Auto colour adding
yellow, and fixed the unsharp mask's fixed 3×3 radius sharpening the export ~2.7×
more finely than the preview. 1.2.0 stopped the crop quad being pinned to the
photo's own border (the *"stretched wrongly"* report) and moved the progress
overlay so the import counter is visible where imports start; 1.1.0 added *Undo
all*, manual corner handles, and the deskew guard that refuses a score curve with
no peak in it. README carries a short per-build list (`### What each build
changed`); the number exists so a deployed copy can be told apart from a local
one, and the user has to re-drag `dist/` to Netlify for it to change there.

## Architecture

Page model: source `<img>` (blob-backed JPEG, capped at 2400px) + coarse
rotation + fine de-skew angle + a **normalised** corner quad + mode + adjustment
values. Derived canvases (`_oriented`, `_rects`) are cached three-per-page and
released on leaving the editor.

Pipeline: `orientedCanvas` (coarse rotation) → `rectify` (de-skew rotation
folded into the quad, then a homography warp with bilinear sampling) →
`enhance` (auto levels / shadow removal / adaptive threshold / unsharp).

### One panel, one preview, and the preview is the output

Cropping and cleaning are two halves of one job, and behind tabs the result of
one was never visible while setting the other. They share a single `#panel` of
two `.ctl-row` lines, and the stage shows **only the finished page** — the same
pixels the export writes — so there is no mode in which the preview is lying
about what you will get.

The stage is the whole of the editing surface. There is **no second view of the
source and no hold-to-compare**: straightening is Auto crop, the 90° rotate
buttons, the fine-angle slider, Undo all, and the crop handles. This was arrived
at in three steps and all of them are worth recording, because two of the
intermediate designs were reasonable and only one was right:

1. The corner handles cannot sit on top of the output they are transforming, so
   they were moved to `#src-inset`, a small source thumbnail with the quad drawn
   over it that could be enlarged over the stage. It worked, and it was tested —
   `tests/ui_flow.py` derived a corner's screen position from the inset's
   rectangle and the source aspect and checked a drag landed there.
2. The user then said they did not need to see the original after each change and
   did not want a small preview window at all, and chose to drop manual corners
   rather than move them onto the big view.
3. Later, with Auto crop refusing frames it cannot read (see **Tilt** below), the
   user asked for the corners back — and the reason they could come back is that
   the first objection no longer applies: the preview *is* the cropped output, so
   the crop quad's corners land on the corners of the preview box, and a handle
   rides the box edge rather than covering anything. The box is the crop. That is
   `js/50-ui.js`: `placeHandles`, `startCropDrag`, `moveCropDrag`, `endCropDrag`,
   over an SVG layer inside `#stage`, with `JS.cropMapper` in the pipeline.

   A drag freezes the mapping at `pointerdown` — the oriented canvas, the quad in
   oriented pixels, the output size and the inverse homography — and re-renders at
   that **frozen** output size (`JS.cropPin`, part of the buffer cache key) so the
   frame never moves out from under the finger while the image warps inside it. A
   move that would make the quad concave or folded is refused by `JS.quadOk` and
   the previous value kept; convexity is judged in the un-rotated `page.corners`
   frame, which is why a corner dragged exactly onto the line between its
   neighbours is refused rather than accepted as a sliver.

   **There are eight handles, not four** (1.5.0). One on each corner and one on
   the middle of each side, in a fixed clockwise table (`HANDLES` in
   `js/50-ui.js`) — the corner ones are indices 0, 2, 4, 6 and the side ones 1, 3,
   5, 7, so a handle's kind *is* its index parity. The corner handles move one
   point; a side handle translates **both** of that side's corners by one delta in
   the normalised frame, which is the fit Auto crop is most likely to get wrong —
   a page lying on a shadow has one edge it cannot see, and one drag beats two
   corners that have to be made to agree. A side drag reads its start corners from
   `cropDrag.start` rather than from the live page: a delta applied to the live
   corners accumulates once per `pointermove` and stretches the pair apart instead
   of sliding it.

   One defect here was found by the probe rather than by a user, and it is worth
   recording because the code looked correct. The finger's u/v are clamped to
   [0,1] by `cropMapper`, but the *offset* derived from them is not — so dragging
   the right-hand side handle of a page already cropped to the photo's own edge
   produced a TR at x = 1.09, `JS.quadOk` refused the whole move, and the handle
   was live, drawn, and did nothing at all. The delta is now clamped to what keeps
   both moving corners on the photo, so a side already on the edge slides along it
   instead of being refused. The untouched side never moves, and that is asserted.

So the *inset* surface is gone rather than merely hidden, and the removal is
pinned as such: `ui_flow.py` checks the DOM nodes are absent, that no canvas
remains in the stage but the preview, that `app.comparing` / `app.insetOpen` are
not on the state object, and that `JS.normToBox` / `JS.boxToNorm` /
`JS.drawInset` / `JS.setInsetOpen` are undefined. A removed control that leaves
its state and helpers behind is the usual way a UI removal rots.

`JS.fitBox` (`js/00-utils.js`) survives on its own: it letterboxes the finished
page into the stage, which is also what puts the handles where the drag maths
expects them. It is called on a box `HANDLE_PAD` smaller than the stage, because
the stage clips the handle layer and a dot centred on the clip line is a
half-disc over a pixel that hit testing cannot reach — measured, at every one of
the five phone sizes, and pinned by a mutation that sets the margin to zero.

### The stage is what the panel leaves

The user reported the page at "like 1/4 only on my mobile" and having to scroll
to reach Done and Auto clean. Measured at 375×667: the stage was **29.2%** of the
screen and `#btn-magic` ended at y=743 against a 667px viewport, 76px below the
fold.

Neither number was a bug in the sense the earlier ones were. The editor is a
fixed column — topbar, stage, panel, footer — the stage is `flex: 1 1 auto`, and
the footer is `flex: 0 0 auto`. So the stage is *whatever the others leave*, and
the only thing that decides its height is the cap on the panel: `max-height:
42vh`, which on a 667px phone is 280px and on every phone was more than the page
got. The fix is that one number, `min(26vh, 210px)`, plus the chrome around it:
`--tap` 44 → 40, the topbar and panel paddings tightened, the pager row folded in
beside Done (36px), and `height: 100dvh` on `.view` so the column is the part of
the screen actually on show rather than the taller layout viewport the URL bar
leaves behind.

Measured after: 47.5% / 50.1% / 54.1% / 57.8% at 375×667, 360×740, 390×844 and
430×932, with Auto crop, Auto clean, Done and the pager all inside the viewport
at every one of them, and nothing pushed off the bottom.

**The defaults had to leave the panel.** They were the first row of each half,
and the panel's content is ~406px against a 210px cap — it scrolls at every
phone size, so being "the first row of a group" put Auto clean in the scrolling
region. Both now sit in the footer with Done, which never scrolls.

**And the panel's order became load-bearing.** Capping the panel at 26vh meant
its first ~173px are what you can see, and the mode chips — which were then
second, after the crop half — fell outside that at *every* size, including the
ones where they had previously been fully visible. That is a regression the
change introduced, and it matters for a reason that is not about convenience:
`Auto clean` is pinned, and the mode is its only input, so a pinned button that
will not say which of the modes it is about to apply is worse than one you have
to scroll to. The halves are therefore ordered tone-first, against the workflow
the panel is named after. Rotating by hand is the rescue path for when Auto
crop misses; choosing a mode is per page.

The panel also gained a scroll shadow (the `local`-over-`scroll` gradient pair),
because with the cap doing its job the last row that fits is a button ending
flush with the edge — which reads as the end of the list.

### No scrolling: the panel is what it needs, and the stage is what is left

The user came back with *"put all the buttons / slider on 1 single page including
the picture. i do not want to have to scroll up and down to find the done
button. make all button smaller."* Done was already pinned by then, so the
complaint was the panel's own scroll: capped at `min(26vh, 210px)` against ~406px
of content, it scrolled at **every** phone size, by 233px at 375×667.

That cap was the previous fix and it worked by making the panel a fixed slice of
the screen. This requirement inverts it: **the panel is sized by its content and
the stage absorbs the difference.** What used to be "the stage is what the panel
leaves" is now "the panel is what it needs, and the stage is what is left" — a
browser that renders a row a few pixels taller costs the page a few pixels
instead of hiding a control.

The content had to come down from 406px to ~222px to make that affordable. Every
number, measured:

| Change | Saved |
|---|---|
| `--tap` 40 → 34, `.btn` 12.5px/`0 11px`, topbar and footer padding 8/10 → 6/8 | ~30 (chrome, 8 rows) |
| The crop group's three rows → one (`⟲ Left` / `⟳ Right` / `Undo all`) | 47 |
| `Reset tone` off its own row and into the drawer with the sliders it resets | 39 |
| The crop hint paragraph deleted; its content moved to Help, and the stage hint already says it contextually | 37 |
| `.chip` 12.5px/`6px 12px` → 11.5px/`3px 9px` (still two rows at 375; one at 412+) | 17 |
| `.slider-label` 12 → 11.5px, range input 22 → 20px, panel/group margins 7 → 5 | ~25 |

Measured after, at 320×568 / 375×667 / 360×740 / 390×844 / 430×932: panel scroll
**0px at all five**, every visible control painted inside the panel's box, every
control inside the screen, footer never pushed off, page at
**35.1% / 44.8% / 50.3% / 56.4% / 63.5%**.

**The trade, stated rather than glossed:** the arrangement that scrolled kept the
page at 47.8% at 375×667 — three points *more* than the 44.8% this one gave. The
picture and every control together are more than 667px, so one of the two requests
has to give, and the page gives. At 320×568 both cannot be met at all and the page
was 35%. `ui_flow.py` asserted the 47% figure against the replay so the price
stayed visible.

*(Superseded by 1.4.0 — see **Two lines instead of two groups** below. The 1.4.0
arrangement is 74.4% at 375×667 with nothing under a fold, so the trade described
here no longer exists: the height stopped being the cost once the panel became two
lines. The replay check survives with a floor of 46%, which the rebuilt old panel
clears at 55%.)*

**One control is deliberately not on that one screen.** The Custom drawer is eight
sliders plus *Reset tone* — ~340px on their own, more than any phone has to spare.
It is the only thing in the editor behind a tap, and open it is the only thing
that scrolls. `Reset tone` went inside it, which is where it belonged anyway, and
the escape hatch for anyone who does not want to open a drawer is *Auto clean*,
which is pinned and is a strict superset of it: `autoEnhance` sets `bright = 0`
and `warmth = 0` as part of applying the mode's preset, so it clears exactly what
`Reset tone` clears.

**`flex-shrink: 100` on the stage against the panel's 1 is load-bearing.** Both
are content-sized, so the default split takes a few short pixels off *both* — and
a panel 5px short of its content is a panel that scrolls, which is the one thing
this layout exists to prevent. At 360×640 that showed up as exactly 5px of
scroll. Weighting the shrink makes the stage give way first, all the way to its
90px floor.

The panel kept `overflow-y: auto` and a `min(58vh, 330px)` cap as a safety valve,
not as the layout: it binds only when the drawer is open or the screen is too
short to hold the column. The floor — 47px topbar, 90px stage, 89px footer, 10px
of margins — is 236px, so nothing overflows above that.

*(The 222px quoted in the 1.1.0 section above is that build's own accounting, and

Four decisions the user made when asked, all applied: the **`Original` chip is
dropped** (a button for the state the page is already in); the tone row's label is
shortened to `Tone:`; the **✨ is dropped** from the three auto buttons, which is
what makes four fit on a 300px line; and a corner grab **auto-zooms onto that
corner** rather than offering a zoom button.

Three decisions were taken without asking, each because the alternative did not
fit:

- **The pager moved to the topbar**, around the "2 / 5" it moves. Two arrows plus
  Done plus three auto buttons is six controls on one 300px line; something had to
  move, and the page position reads better next to the page number than next to
  the four buttons that *change* the page.
- **The mode name took the label's place** rather than following it. `#mode-name`
  sits inside the `Tone:` label span and replaces the word when a chip is not lit
  — *Receipt* has no chip, so on a receipt-cleaned page there would otherwise be
  nothing on screen saying which mode was applied.
- **The rotate glyphs are dropped.** `⟲ Left` costs 13px off the fine-angle
  slider: measured at 320px, 68px of travel without the glyph and 39px with, and
  ±15° over 39px is a slider you cannot set. The `aria-label`s still say what the
  buttons do.

The drawer had to stop being a `<details>`, and the reason is a flex one: a
`<summary>`'s drawer opens *inside* the summary element, so in a flex row the
sliders would open inside the chip. It is now `#chip-custom`, a button with
`aria-expanded`/`aria-controls`, toggling `#tune`'s `hidden`. That has a
measurable consequence for the tests: `[hidden] { display: none !important }`
means the drawer's subtree has **no layout at all**, where a closed `<details>`
was laid out but unpainted — so a probe that filters on `getClientRects().length`
is now required where the old one filtered on `details:not([open])` (see
**Evaluation standard**).

### The view: one transform for the canvas *and* the handles

`JS.getView()` returns `{z, tx, ty}` — a scale about the stage's top-left plus a
screen-pixel translation. It is applied as one CSS transform on `#stage-zoom`, a
wrapper holding **both** the `<canvas>` and the crop-layer `<svg>`. Two elements
scaled by two styles drift apart by a fraction of a pixel at the corners, and a
handle half a pixel off its corner is a crop half a pixel wrong — the one place
they must agree. The hint stays outside the wrapper, because a message about the
page should not be magnified with the page.

`JS.viewZoomAt` scales about a point and holds it still (what makes a pinch feel
attached to the fingers), `JS.viewPan` is at screen speed, and `JS.VIEW_MAX = 6`
because past that the preview is upscaled from fewer pixels than it is drawn at.

**`JS.viewClamp` is the centre rule, and that is the load-bearing choice.** The
image's own centre must stay inside the fitted rectangle — one clamp per axis. It
is deliberately *not* the cover-the-box rule a photo viewer uses, because of the
corner grab: the grab zooms about the corner's own position, and for a letterboxed
page the corner sits `fit.x` in from the box edge, so a cover clamp moves the dot
out from under the finger by exactly `fit.x` (43.5px on a real phone) and
`fit.y` (11px). The centre rule holds all four corners **exactly** — verified
numerically and mutation-tested in `smoke.js` against an inline cover clamp, which
fails the same four checks by exactly those amounts.

Two consequences that make it safe:
- At fit zoom there is exactly one allowed view and it is the identity, so a pan
  (or a stray fingertip) on an unzoomed preview cannot move anything, and there
  is no way to lose the page — which matters because there is no scrollbar and no
  reset button.
- The strip of empty stage the loose rule permits is small and exists only just
  above fit zoom: over every pan the clamp allows, the emptiest stage still shows
  **74.9%** page against the **72%** the fitted view itself shows, and past 1.33×
  the page covers the stage on both axes.

The corner grab is `JS.CORNER_ZOOM = 2` about the handle's own stage position, and
release restores the pre-drag view. A drag while zoomed tracks the finger 1:1
because the crop mapping is in stage coordinates and the transform is outside it —
`ui_flow.py` asserts the dot lands exactly `40 / (w·z)` of the page across when
the finger moves 40px on screen.

`JS.getView()` returns the module's own `view` object rather than reading the
computed style back, so every one of these is checkable in `smoke.js` with no
layout at all. (`app.view` is a different thing — it is the *screen* name,
`'home'` or `'edit'`.) `setView` resets the zoom on the way out of the editor,
alongside taking the handles off, because the next page opened has no relation to
where this one was being looked at.

### One button that does both, and a chip that became a decision

The user came back with *"remove the receipt button. rename auto detect asn auto
crop. put a button btewwen auto clean and auto detect, called Auto all"* — three
changes that turn out to be one idea: stop asking the user to choose a crop, a
tone and a receipt-ness separately when the app can infer all three.

**The `Receipt` chip is gone; the mode is not.** `JS.suggestMode` has always
picked a mode from the shape of what was cropped — over 2.1:1 it returns
`receipt` — and `JS.autoAll` has always called it. Both were dead code: written
into `js/30-pipeline.js`, called from nowhere, referenced by no test. Removing
the chip is therefore not removing the mode, and the test asserts all three
facts separately: no chip with `data-mode="receipt"`, the other three mode chips
still there (and only those — Greyscale left in 1.3.0), and
`MODE_DEFAULTS.receipt` / `MODE_LABELS.receipt` still defined.

> **Reversed in 1.6.0.** The chip is back, and `autoAll` no longer calls
> `suggestMode` at all. Removing the chip and teaching *Auto all* to pick the
> mode were two halves of one decision, and the user rejected both halves
> together — see *Auto all stops picking the mode, and Receipt gets its chip
> back* below. What survives from this section is the reasoning about the footer
> row and about the hint reporting both halves of what a button did.

**`Auto all` is the wiring, not new logic.** `JS.autoAll` existed and was
unreachable; the work was a listener. One contract change was needed:
`autoAll` returned `mode` and threw away what `autoDetect` reported, so a caller
could not tell "cropped and cleaned" from "found nothing and cleaned". It now
returns `{found, skew, mode}` and the hint reports both halves — `Cropped · tilt
0.0° · Receipt` or `No clear page edge — cleaned as Receipt`. A button that
reported one half would be the same lie as one that reported neither.

**The footer row is the constraint.** Three buttons and three sparkles in a
300px row at 320px: each button is 96px, the border and padding leave the
longest label (`✨ Auto clean`) 76px, and it wants 81px. The 9px padding is what
absorbs that 5px so the ink stays inside the button — this is why `.btn--auto`
sets its own `padding` rather than taking `.btn`'s 11px. The sparkles were
briefly removed on a false premise and put back: the measurement that condemned
them had cloned the button with a 16px `.btn-ico` span, which is the *home*
footer's icon size; as plain 12.5px text they cost nothing like that.

**This row fails by painting over its neighbour**, because `.btn` is
`white-space: nowrap` — it never wraps and never widens the row, so the row stays
inside the screen and every other check in `ui_flow` stays green. The new check
therefore measures the painted label against the button's own box, and it
measures it with a `Range`, **not** `scrollWidth`: the first version used
`scrollWidth` and passed a row whose label had been deliberately lengthened.
Scrollable overflow does not include the inline-start direction, and `.btn`
centres its content, so a too-wide label spills equally both ways and the half
`scrollWidth` can see is nothing. This is the third variant of the same trap in
this file — an element that *is* wrong while its obvious numeric measure says it
is fine — after the clipped-element rect and the closed `<details>` subtree.

### A chip that has been lit can be put back

*"when i click auto color again, it must undo only auto color. same for b/w
button."* Until 1.5.0 a mode chip was one-way: `setMode` wrote the mode's preset
over `page.adj` and there was no record of what had been there, so the only route
back was *Undo all*, which throws the crop and the straightening away with it.
The user chose **"restore what was there before"** over the alternative of
re-applying the neutral defaults, which is the difference between a toggle and a
reset.

`JS.setMode` now keeps two small fields on the page — `modeTap`, the mode that
was live when the chip was lit, and `modeBack`, a copy of the five adjustments it
overwrote (`MODE_KEYS = ['flat', 'thr', 'contrast', 'wb', 'sat']`). Tapping the
lit chip again writes `modeBack` back, restores `modeTap`, and clears both. Three
consequences are asserted rather than assumed:

- **It reaches Receipt, which had no chip in 1.5.0.** Receipt was the mode Auto
  all picks on a strip and the one a user is most likely to be sitting in; the
  memory is a *mode*, not a chip, so the round trip Receipt → *Auto colour* →
  *Auto colour* ends in Receipt with Receipt's own values. Receipt has had a chip
  since 1.6.0, which makes this round trip *easier* to reach rather than
  different, and the check is unchanged.
- **It is exactly a tone change.** Crop, `fine`, `coarse`, `sharpen` and the view
  are provably untouched — the check hashes the preview's pixels before and after
  and requires the same hash, not merely the same numbers, because equal state
  that renders differently is not a restored page.
- **Tapping the *other* chip in between is not an undo.** Lighting B/W after Auto
  colour overwrites the memory, which is what makes the second tap on B/W mean
  "put back Auto colour" rather than "put back whatever was there two taps ago".

`JS.undoAll`, `JS.resetAdjust`, `JS.applyToAll` and `JS.duplicatePage` all clear
`modeTap`/`modeBack`: after *Undo all* the next chip tap is a first tap, and a
duplicated page must not inherit a memory of a tone it was never in.

### The threshold now reads contrast

*"auto clean must use ML to clean, not hard algo. why? sometimes the words get
broken after cleaning when it is a bit thin or blurry"* — and the user chose
**fix the algorithm** over shipping weights, with the constraint that it stay
offline, instant and dependency-free.

The old rule was Bradley–Roth: a pixel is ink when it is darker than the local
mean. On a thin or soft stroke the window's mean is dragged **down** by the stroke
itself, so the test tightens exactly where the ink is faintest, and a stroke that
wavers across the line comes back in pieces. The new one is Sauvola —
`T = mean * (1 + k * (std / R - 1))`, R = 128 — which adds the window's **local
contrast**. A flat window (std → 0) gets `T → mean * (1 - k)`, stricter; a window
a stroke runs through (std → R) gets `T → mean`, the old rule; and since std never
exceeds R in practice the new threshold is **always ≥ the old one**, so the change
can only add ink. That property is a test, not a claim: `smoke.js` counts the
pixels Bradley called ink that Sauvola does not, and requires zero.

why `JS.runMagic` asks about `'original'` alone and why the guard is correct
rather than a bug — the frame is what it can honestly measure. If a user still
sees broken words on a page that never crops past 2.1:1, what they are looking at
is the continuous-tone path, and no threshold change will touch it.

> **In 1.6.0 only *Auto clean* reaches it**, and only for a page in `original` —
> *Auto all* no longer picks a mode at all, so it applies whatever tone is
> already in force. The paragraph above is the reason the two lines above it were
> ever distinguishable; it is kept because the measurement in it still governs
> *Auto clean*.

`JS.adaptiveThreshold` is kept and still tested even though it now has no

### Auto clean does not compound, and the two buttons now agree

The user came back with a report rather than a request: *"when i click auto all,
i still see some shadows. then i click auto clean and the shadows disappaers. so
it is that auto clean can be clciked many times to futher clean noise and
shadows?"* The answer is no, and the interesting part is why the app could look
as though it were yes.

**`autoEnhance` is a state assignment, not a filter.** It writes absolute
per-mode values (`page.adj.flat = d.flat`), and `autoAll` calls it — so the state
after *Auto all* is already the state *Auto clean* would produce. Measured on
four fixtures with the preview canvas hashed pixel-for-pixel: identical state
key, identical pixels, and a second *Auto clean* is a no-op. Clicking it
repeatedly cannot clean more because there is nothing left for it to change.

**But it could look otherwise, and the app was hiding the reason.** *Receipt* had
no chip in 1.5.0, so when *Auto all* picked it, `syncEditorChrome` lit **no chip
at all** — four dark chips and a stage hint that fades after two seconds. A page
cleaned as a receipt therefore looked like a page nothing had been applied to,
which is exactly the reading that makes *Auto clean* look like the button that did
the work. The mode was then named at the right of the *Clean & Tone* title when
no chip was lit, and silent when one was. It was the second half of the cost of
removing the chip, and the first was the hint wording.

> **That slot is dead in 1.6.0, and this is why.** Now that Receipt has a chip
> again, the only mode without one is `original`, and `syncEditorChrome`
> short-circuits that case — so the name slot is written `''` for every state the
> app can reach. The DOM, the CSS and the write are all still there and the tests
> still assert the slot exists and is empty, because deleting a working safety
> net to save one `textContent` write is not a trade worth making. What was
> *removed* is the mutation test that used to guard it: with the string always
> empty, silencing it is an equivalent mutant.

**And the buttons really did disagree in one place.** `runMagic` hard-coded
`page.mode = 'auto'` when the page was in Original, while `autoAll` asks
`JS.suggestMode`. On a receipt those are different modes — threshold path versus
continuous tone — so *Auto all* and *Auto clean* rendered visibly different
pictures from two buttons that read as the same job. `runMagic` now asks the same
question, and the only thing *Auto all* does that *Auto clean* does not is the
crop. The mutation that reverts it breaks exactly one behavioural check.

**What could not be reproduced, and what was not claimed.** Neither fixture could
reproduce the report itself: in both, the detector crops the shadowed band *away*
(the pre-existing behaviour — it takes the lit part of the sheet as the page), so
there is no shadow left inside the crop for the two buttons to differ about. The
literal sequence was then run both ways, plain and with an Original detour, on
both fixtures, with the mode, the chips and the hint printed at every step — and
the only divergence found is the one above. Rather than assert a cause that the
evidence does not support, the answer to the user is the measurement plus the one
defect it did find, and a request for the photo if shadows still survive *Auto
all* on a page whose shadow is not cropped off.

### Auto all stops picking the mode, and Receipt gets its chip back

*"auto all is only auto crop and auto clean only"* — offered as a description and
confirmed as a request: **Auto all should stop choosing the mode.** It should
find the page and apply the tone of whatever mode is already in force, and leave
the mode alone. `JS.autoAll` therefore drops `JS.suggestMode` and the
`page.mode = mode` write, returns `{found, skew}`, and its doc comment no longer
claims it "goes on to pick a mode and clean".

**The consequence had to be paid for, not argued away.** A fresh photo starts in
`auto`, and `JS.runMagic` only consults `suggestMode` when the mode is
`original` — so *Auto all* was the only route into `receipt`, and removing the
guess would have made the mode unreachable. The user chose **put the Receipt chip
back**, which also un-does the 1.5.0 decision recorded above. The two changes are
one trade and are only coherent together.

**And the fifth chip costs the stage 27.6px if the row is allowed to wrap.** The
tone row at 320px shares its width with a `Tone:` label and the Custom chip, and
has **198.0px** to lay chips in. Five chips spelling the modes out in full — the
four that shipped plus `Receipt` — need **231.0px** and wrap to a second line,
taking the row from 24.7px to 52.3px and the stage from **70.0% to 65.1%** of the
screen. That is not a marginal loss; it is a quarter of the slack the stage-share
floor is protecting.

`tests/tmp/chip_row.py` sweeps five levers across five phone widths, and
`tests/tmp/chip_slack.py` measures the honest quantity — the free space in
`#tone-row`, since a `flex: 0 1 auto` child that fits is exactly content-sized and
its own `clientWidth` therefore says nothing about how close it came. (The first
version of that probe measured `#mode-chips` and reported a bogus −0.2px.) Padding
alone was not enough: 5px and then 4px each still wrapped with the full label
(215.0px). Keeping every word needs font 10.5px *and* padding 3px 3px — a 9% type
shrink with tighter tap targets than any other chip in the row, which is a worse
trade than an abbreviation.

So the chip reads **Colour**, and the CSS goes to `gap: 2px` / `padding: 3px 4px`.
The abbreviation has precedent inside the same row: `B/W` has always stood for
the mode `JS.MODE_LABELS` calls `Black & white`. The mode is still *Auto colour*
everywhere it is named in prose. The result is **12.3px of slack** at 320px, one
line at all five widths, chips reading `Colour / Receipt / Sharpen / B/W`.

**Slack was treated as the point rather than the fit.** A 1.8px fit is not a fix
— a wrap is a cliff, not a slope, and a slightly wider font or a longer
translation takes the whole 27.6px back at once. 12.3px is the margin that makes
the next label change survivable.

**The guard that should have caught this could not see it.** `rowFit` compared a
row's height to its *tallest child*, and a flex child that wraps internally is
still only as tall as its own box — so a two-line `#mode-chips` read as a
one-line row. The stage-share floor was the only check that noticed, which is not
what a guard is for. `rowFit` now also reports `subWrap`, asking each child the
same question it asked the row, and the tone-row and crop-row checks require it
empty. `tests/tmp/chip_guard.py` falsifies it by painting the old configuration
back on: as shipped `ok` at 70.0%; with only the word reverted, **FAIL** —
`subWrap ['mode-chips']`, 65.3%; with the word and the CSS reverted, **FAIL**,
65.1%.

One thing had to change for that guard to work at all: `worstToneLabels` used to
force `#mode-name` to `"Black & white"` as well as the Sharpen chip to
`"Sharpen 3"`. Now that every reachable mode has a chip, `syncEditorChrome`
writes `''` into that slot in every state, so forcing it measured a state the app
cannot reach — and once the guard could see a wrapped child, that unreachable
state failed the check on its own fixture. The Sharpen arm stays, because that
chip is real and `"Sharpen 3"` is three taps away.

### Edges are fitted, not cornered

Auto-detect no longer reads four corner points off the page region. It buckets
the boundary pixels onto the four sides, throws away the outer `band` of each
side, and fits a line through what is left; the corners are the intersections of
those four lines. `refineOnce` refuses to return anything unless *all four* sides
fitted, because a quad stitched from three fitted edges and one inherited from
the rough shape looks like an improvement and passes every geometric check while
having moved a corner on no evidence at all.

`sideCore` drops both ends of each side for two reasons that point the same way:
a point near a corner is genuinely on two sides at once and tilts both fits
outwards, and a shadow blob stuck to a corner is real boundary by every measure
except that it is nowhere near the corner. Three points is the floor — two
define a line but say nothing about whether it bends, and one is what a corner
swallowed by a protrusion leaves behind, which is not evidence about that side.

`JS.fitLine` takes the principal axis of the covariance rather than a y-on-x
regression, since a page edge runs in whatever direction the page is rotated to
and a regression blows up as the edge approaches vertical.

### Boundary points are the sheet's outline, not the printing on it

This is the correction that fixed the user-reported crop, and the reason it was
invisible for so long is that it is decided one layer *above* everything the
tests were looking at.

`JS.boundaryPixels` used to return every page pixel with a non-page neighbour.
That sounds like the outline and is not: a glyph is a hole in the bright region,
so its rim is a page-pixel-with-a-non-page-neighbour too, and a page of text is
mostly holes. On the photograph that started this, the outline contributed 1200
points and the printing 2754 — the printing outnumbered the paper by more than
two to one, and the four fitted sides landed on the paragraph margins. The
visible result was a crop around the text block: `ATHLAB` missing its first
letter, `CLIENT ID` its first two.

The fix tells the two apart by **reachability**. The desk below the page is a
non-page region you can walk to from the frame border; a glyph is one you
cannot. One flood fill of the non-blob region from the border marks every
outside pixel, and a page pixel is on the silhouette if it faces one — or if it
sits on the frame itself, which for a page shot to the edges of the frame is the
only evidence that side has at all. Boundary points on the real photo fell from
3954 to 1200, and the crop became what the user expected: full width, full top,
floor gone.

Two further guards came out of the same investigation:

- **`robustLine`** replaces the bare least-squares fit. A side's bucket can hold
  the page edge *and* the rim of a shadow lying across it, and least squares has
  no opinion about which inputs deserve to be there — it splits the difference
  and is then wrong about both. The fit is now the line most of the points agree
  on (candidate lines from pairs half a set apart, so a spread of pairs finds
  the real edge with nothing random in it), refit twice on its own inliers.
- **A residual guard** rejects a side whose points no single line describes
  (`rms > max(2, 1% of the side's length)`). Refusing one side refuses the whole
  refinement, which is the safe direction: the rough quad stays.

`JS.boundaryPixels` is exported for exactly one reason — the distinction it
makes is not observable downstream. A fit handed a bad point set can still
return a plausible quad, and on the full-frame test photo the *old* function
still produced the right crop. `smoke.js` therefore counts the points where they
are decided. That section carries its own falsifier, in the shape of
`oriented_render.py legacy`: it re-evaluates the module with the old
`boundaryPixels` in a throwaway `vm` context and requires the checks to break.
The substitution is asserted, so a rename cannot quietly turn the block into
three tautologies.

### A background is a border that is decisive *and* one material

The user reported a second wrong crop, on a different photo: a pale taxi receipt
held between finger and thumb over pale mottled marble. The detector (Auto
crop) cropped a
slice of the hand covering 15% of the frame and said "Edges found". Two
independent defects were behind it, and each was found by measuring the user's
actual photo rather than reasoning about the code.

**1. The background reference was a coin flip.** `quadFromGray` reads the
frame's border to learn what the background is, then masks the class on the
*opposite* side. On this photo the border mean was 166.3 and the Otsu split was
165.0 — 1.3 levels apart — so which side the paper was on was decided by
nothing. The mask selected the dark class, and the largest dark region in that
frame is the shadowed hand.

The first guard written for this was "refuse when the border mean sits within
`delta` of the split", and it broke the easiest fixture in the suite: a bright
sheet on a uniform dark field has its border mean exactly *on* the Otsu
threshold, because Otsu returns the last bin of the dark class and that class is
the background. Margin 0 there is the ideal, not ambiguity. `smoke.js` caught it
in one run, which is what that suite is for.

Border **spread** is the quantity that separates the cases, and it is the
physically right question — a background is only a background if the border is
one material. Both conditions are needed, each catching what the other misses:
the spread alone would refuse a page filling the frame, where the border is
legitimately part page and part background. Measured across the fixtures:

| frame | margin | border sd | |
|---|---|---|---|
| receipt on a desk | 82.0 | 0.0 | keep |
| page on a floor | 85.0 | 0.0 | keep |
| page filling the frame | 43.8 | 74.4 | keep |
| sheet on a dark field | 0.0 | 0.0 | keep |
| receipt on marble, in a hand | 1.3 | 64.8 | refuse |

**2. The fine skew scan chased its own bound.** `for (a = best - 1; a <= best +
1; a += 0.2)` uses `best` as its own loop limit while the body updates `best`.
On the failing photo it ran **63 iterations instead of 11** and walked the answer
to 18.4°, which the caller's clamp turned into a flat **−15.00**: a full-scale
rotation, at the limit, out of a profile with no peak in it.

Refusing a peak at the scan boundary is the fix, and the coarse scan was widened
from ±8° to the slider's own ±15° at the same time — not to find more tilts in
noise, but because the shape that matters is *where* the maximum sits, not how
big it is. The score has a second way to rise, unrelated to alignment: rotating
further swings ink out of frame, and discarding ink raises the variance of what
is left. On a frame with no text lines that drift is the only structure there is,
so the maximum walks outward to the bound *however wide the search is made*.
Uniform noise peaks at ±15 monotonically; so does the failing photo. Every
synthetic page with a real tilt peaks interior, an order of magnitude above the
drift. So the widened scan recovers 8°, 9°, 12° and 14° — which the old ±8 bound
had clipped to 8 — and still refuses noise, 15° and 20°.

The reported photo is now refused on both counts (`skewFromGray` also returns 0
for it), and the app says *"No clear page edge found"*.

### The paper's own level, as a second candidate

The polarity guard above refuses a frame whose border straddles the split. It
does not help a frame whose border is perfectly decisive and whose *page* is
still mis-measured — which is the reported taxi receipt. There the split lands at
a level where the receipt's right edge and the shadow beside it are the same
tone, so the mask's boundary runs down the shadow and the fitted right side
slants diagonally across the paper, taking the amounts column with it. Nothing
about that frame is ambiguous; the one threshold is simply in the wrong place.

So the detector asks a second question about the same frame: *where is the paper
itself*, rather than *where does this frame divide*. That is a mode, and the
whole difficulty is the word.

**Mass is a floor; prominence is the test.** Paper is a large flat surface lit
evenly, so it puts a real mode in the histogram. A reflection, a shadow or a hand
is a *ramp* and puts a ramp there. The first version asked only whether a 21-level
window around `v` held enough mass — but a window wide enough to hold a page's
spread holds a ramp's too, so on any frame with a gradient every station
qualified and the function returned the top of the ramp. The test is instead that
a peak stands above its own shoulders, `sm[v-24]` and `sm[v+24]`, by a quarter of
its own height: true of a flat surface by construction, impossible on a ramp,
whose density at `v` and at `v ± 24` is the same number. Mass is still asked for,
off the *raw* histogram over ±10 levels so the window is really 21 wide rather
than 33.

**A shoulder that runs off the top of the histogram is not a shoulder.** The
first version clamped the right reference into the top bin, `sm[255]` — which is
*the peak itself* whenever the mode sits near the top, so prominence came out at
or below zero by construction and the brightest thing in the frame was the one
candidate the test could never accept. A white receipt in daylight is saturated
at 255, so that is not an edge case, it is the paper. Measured as prominence out
of the peak's own height:

| frame | peak | share of frame | clamped | unclamped |
|---|---|---|---|---|
| `pair1` | 249 | 28.2% | **6%** | 94% |
| `set25` | 249 | 52.6% | **20%** | 89% |

With the clamp in place `pair1`'s scan walked back down to a 4.3%-mass midtone
peak at 121 and reported it as the paper's level. Both frames lost their second
candidate, which is what ui_flow's *"the paper-mode candidate is found where the
paper is saturated"* pins.

`modeValley` then cuts between the background and that mode. Its search floor is
halfway between them, and on a histogram that rises monotonically across the
whole range the argmin lands *on* that floor — which is where the mixed-tone
falsifier's threshold of 215 comes from. That is not a defect to fix: the floor
is a defensible place for a threshold even when the histogram has no valley, and
the mask it produces is judged on its own merits like any other.

**The two candidates, and the guard between them.** `candidateQuad` masks the
class opposite `thr` *and* at least `delta` from the background's own mean. The
second threshold can therefore flip which class that is — at 215 on the
mixed-tone frame the background reads as dark and the mask takes everything
above it, the counter and the receipt together, scoring 40.7 against the loose
candidate's 8.3 and winning. That is the reported crop-a-hand bug arriving by a
new route, and it is refused: **the second threshold must agree about which side
of the background the page is on.** No fixture reaches it — the polarity guard
refuses that frame before either candidate exists — so it is a guard on the new
path, and `smoke.js` mutates it by cutting its source text.

A candidate is scored on the worst side and the interior: the mean inside-minus-
outside step over the middle 70% of each side, minimum over the four, plus 50×
the fraction of a 6×6 interior grid that sits at the paper's own level. The ends
of each side are excluded deliberately — a corner is where a curl or a shadow
lives, and the acceptance test should not be decided by it.

**The second candidate is only ever *tried* when the first succeeded**, which is
what keeps this change from touching any frame that is refused today: a frame
whose only answer is the paper-mode mask is a frame where the split mask found
the wrong object, and rescuing that would be a new behaviour on every declined
photo, deciding something this change is not entitled to decide.

**And it has to be worth 25 points more before it displaces the first.** The
split mask is what the app has shipped, so it is the prior; swapping a crop that
is already right is a regression even when the new answer also looks reasonable.
That margin is why `pair2` (26.8 against 21.4) and `pair4` (34.4 against 32.4)
keep their crops. It is a measured number, not a guessed one — and it is pinned
by a mutation that sets it to zero, because a margin that no test can move is a
comment.

Measured across everything to hand, at the detector's 420px working width:

| frame | split | paper-mode | winner | what moved |
|---|---|---|---|---|
| `ori1` (reported) | 74.0 | **121.6** | paper | right side off the shadow and onto the receipt |
| `pair1` | 80.2 | **151.8** | paper | bottom edge stopped slicing the last two lines |
| `set24` | 115.5 | **145.9** | paper | bottom-left corner 0.56 → 0.81 of paper |
| `set25` | 78.1 | **143.9** | paper | top and bottom edges tightened |
| `ori3` | 44.3 | 49.4 | split | nothing — under the margin |
| `pair2` `pair4` `set22` `set28` | — | — | split | nothing |
| `ori2` `pair3` `set21` `set23` `set27` | — | — | refused | nothing |

`pair1` is the instructive row: its paper-mode crop scores nearly twice the
split one while its corner fractions measure *worse* (0.13 → 0.06 on one
corner). Drawn and looked at, the paper-mode quad keeps the receipt's last two
lines inside the crop and the split one's diagonal bottom edge cuts through
them, so the corner number is what is wrong there — the receipt's bottom-right
is off the frame entirely and no corner metric can score a corner that the photo
does not contain.

### Corner settling was built, measured, and dropped

The other half of the plan was to let each corner walk onto the paper, which is
the obvious way to answer a curled corner. It was removed after measuring it.

On all twelve photographs to hand — the seven `set*`, the four `pair*`, `ori1`
and `ori3` — it moved **nothing**. The reason is structural: the acceptance test
samples 15%–85% along each side, so t = 0 and t = 1 *are* the corners, and a
corner sitting in the background is invisible to the score that would accept the
move. The corner metric that would have justified it is itself unreliable
(`set25`'s corner block reads 100% paper over plain background). And the one
place it was ever observed acting was a mutation path, where it changed a
falsifier's answer — a second code path reachable only by mutation is not
evidence for shipping it. `JS.sideSpans` and `tests/tmp/corner_probe.py` are
kept so the question stays askable.

**The curled corner on `Set30` is therefore unmeasured rather than fixed.** The
only copy to hand is a screenshot of the result; rebuilding a source from it
detects cleanly, every corner above 0.94. Whatever the original photo shows, this
build has not seen it. See *Known limits*.

### A tilt with no peak behind it is not alignment

The two guards above both catch a maximum that runs to the bound — one by asking
where the optimum sits, the other by refusing a peak at the scan's edge. The four
photos in the tilt report (recorded in *Bugs found and fixed during the build*
below) showed a third way an angle gets invented, and neither guard sees it:
dense text under a cast shadow leaves the projection with variance at *every*
angle, so the coarse curve stops being a peak with a floor and becomes a broad
mound whose argmax is wherever the noise happened to sit — interior, and passed
by both guards above.

The statistic that separates the two populations is the curve's **own minimum as
a fraction of its peak**: a real alignment peak is narrow, and fifteen degrees
off it the score has collapsed to a few percent of its height, while a mound
never collapses. Measured on the exact canvas `autoDetect` hands the scan
(`rectify` with `fine = 0`):

| input | min/peak |
|---|---|
| synthetic bar pages, 0–14° | 0.001 – 0.009 |
| realistic document / receipt fixtures, 0–12° | 0.050 – 0.116 |
| the four reported photos | 0.486, 0.591, 0.661, 0.749 |

No overlap, a 4× gap, and the guard sits in the middle of it:
`if (minScore > bestScore * 0.25) return 0`, tracking the minimum inside the
coarse loop that already runs — no extra pass. It is **identical at 0.20, 0.25
and 0.35**, so this is a plateau rather than a threshold fitted to the four
photos. Both earlier guards stay: uniform noise has min/peak 0.086 and would
pass this test, and is refused by the `±LIMIT` guard instead.

Two theories were measured and are recorded so they are not retried — "ink is
thrown out of frame, raising the variance of what is left" is not the mechanism
(8% of ink is lost, 48 318 → 44 547, while variance rises 6.2×), and neither
`at0/max` nor peak falloff separates the populations (falloff reaches 0.74 on
genuine fixtures against 0.79 on the drifts; they overlap).

The honest cost: on real photographs the projector's peak is broad generally, so
Auto crop now straightens **much less often**. On the fixture set it mostly
already returned ~0, so what disappears is the wrong answers, not right ones.
That is the intended trade — a page left slightly tilted is recoverable with the
Fine angle slider or the corner handles, whereas rotating an upright page by 10°
is not.

**The four photos are checked in.** `tests/fixtures/pair{1..4}_reported.jpg`
were recovered from the `_b4` screenshots (see `tests/tmp/make_deskew_fixtures.py`)
and `ui_flow.py` now runs all four through the real `#btn-auto`, asserting no
tilt is invented and that each is still cropped. The check is falsified in the
same run: the pre-guard detector is injected into the live page over pair2 and
must still return **−10.20**, the reported value. All four go to `+0.00` with the
guard in place, at crop areas 0.44 / 0.58 / 0.51 / 0.59.

### The photo's own border is not evidence about the page

The seven photos in the second crop report (`set21`–`set28`, *"some are stretched
wrongly"*) failed a way none of the earlier cases did: the crop came back as a
trapezoid whose corners were **the photograph's**, not the paper's. Rectifying
that to a rectangle shears the paper — which is exactly what "stretched wrongly"
looks like. It is a worse failure than a refusal, because the result is a
plausible-looking page with the text slanted inside it.

The mechanism, traced the same way as before (`tests/tmp/set_trace.py` re-evaluates
the module in the page with per-side dumps spliced in): on these frames the mask
merges the paper with the surface it lies on, so `boundaryPixels` — which
correctly counts blob pixels sitting *on the frame* as silhouette — hands the
fitter long runs of pixels lying along the photo's own edge. `robustLine` fits
those perfectly (rms 0.00, exactly 90.00°) and that line beats the page's real
edge, which is tilted and partly out of frame. Refinement then fails `validQuad`,
so `quadFromEdges` falls back to the rough hull, whose extreme points are the
photo's corners too. Both paths end at the frame.

The fix is in `refineOnce` and `quadFromEdges`:

- **Frame pixels are kept out of the edge fits**, but *tallied* per side rather
  than discarded silently, so the fit can tell "no evidence here" from "nothing
  but the frame here".
- **A quad may inherit the rough edge for at most one side**, and only when that
  side's bucket held no in-frame pixels at all but did hold frame pixels. That is
  the shape of "the page runs off the frame, so the border is where the cut
  belongs" — the full-frame fixture's deliberate behaviour, and it survives. Two
  inherited sides would mean the quad is mostly the frame's outline and describes
  the photo rather than the page, so the pass **refuses**; and with no pass
  succeeded, `quadFromEdges` refuses a hull whose corners lie on the frame.

Alternatives were measured and rejected — raw frame fractions, inlier fractions,
corner counts, frame-side counts, shear and aspect thresholds. Each either
refused the legitimate full-frame fixture or kept `set21`/`set23`/`set27`.

**The honest cost, stated:** three of the seven now report *No clear page edge*
instead of a stretched crop. Measured areas — `set22` 0.705, `set24` 0.524,
`set25` 0.668, `set28` 0.552 crop; `set21`, `set23`, `set27` decline. Under the
pre-guard detector the same three crop at 0.598 / 0.839 / 0.687, so the declines
are the guards' doing and are asserted as such. `fine` is 0.00 on all seven. A
refusal that asks for a manual crop is the better failure; the corner handles
are the remedy.

### The progress overlay belongs to the app, not to the editor

The import counter the user asked for — "uploading 3 of 15" — **was already
built** and had been since 1.1.0; `JS.addFiles` has counted `Loading i of n`
per file all along. It was never seen because `#busy` lived *inside* `#stage`,
and every long job this app has starts on the **home screen**: reading photos in,
then writing the PDF out. An overlay inside the editor cannot be seen from
there, so a fifteen-photo import showed nothing at all. It is now a body-level
child after both views, `position: fixed; inset: 0; height: 100dvh; z-index: 70`
(above the help sheet at 60), sized like the views so it covers exactly what they
cover.

The check is behavioural rather than structural: `ui_flow.py` installs a
`MutationObserver` on `#busy-text`, imports five distinct fixtures through the
real file input, and asserts every `Loading k of 5` was observed **while the
overlay was up and the home screen was the view underneath**. The earlier check
it replaced — `JS.$('busy').hidden && !JS.$('busy').offsetParent` — would have
gone vacuous the moment the overlay became `position: fixed`, since a fixed
element has no `offsetParent`.

### Output size is the average of opposite sides

`rectify` sizes the output to `(top + bottom) / 2` × `(left + right) / 2`, not
the longer of each pair. Shot at an angle the near edge of a page genuinely
measures longer than the far edge — that difference *is* the perspective, and it
is what the warp exists to remove. Sizing to the longer edge keeps it as a
permanent stretch, pulling every pixel along the far edge out to a width it
never had. Averaging splits it: the near edge compresses and the far edge
stretches by the same amount, which is what square-to-the-camera looks like. For
a quad already filling the frame the pairs are equal and the buffer passes
through untouched.

### Shadow removal works in the continuous-tone modes

Illumination flattening used to be part of the black-and-white path only, so a
shadow stayed on the paper in colour, greyscale and receipt output. It now runs
in every mode: a summed-area-table box blur estimates the local background and
divides it out, with `JS.SHADOW_GAIN_MAX = 3.2` bounding how hard it can push.

The gain is derived from **luminance** and applied to all three channels
together. Deriving it per channel would be the obvious implementation and the
wrong one: it would flatten a shadowed red stamp into grey, because the red
channel's own local background is dark and gets scaled harder than the others.
One gain, from luminance, keeps the hue.

Its guard is the ui_flow pair of checks — the shadowed paper must lift by more
than 45 and the gap to the lit paper must close to under 45% of what it was,
*while the lit paper is not dragged down with it*. Disabling `flattenRGB` in
continuous tone fails two of them.

### Paper level, not mean

The user reported that **Auto clean left the shadow on a receipt**. It did, at
the old `flat` default of 45; the defaults for the continuous-tone modes are now
85 (`auto`, `receipt`) and 70 (`bw`), and the receipt's paper comes out at 255
across the whole strip.

Getting there took three wrong turns worth recording, because the *measurement*
was the thing that was broken, not the code:

1. **A mean over each half of the receipt reports ink, not shadow.** The
   fixture's thermal bars stop short of the paper's right edge, so the right
   band is blank while the left band is printed. The mean therefore plateaus
   around a gap of 50 however hard the flattening is pushed. The 90th
   percentile of a band is the paper, ink or no ink. Measured that way, flat 45
   leaves 39% of the shadow and flat 85 leaves none — the *same renders* that
   the mean called 106.8 and 50.7.
2. **The gain cap is not the limiter.** Sweeping `SHADOW_GAIN_MAX` over 3.2,
   4.0, 5.0, 8.0 and 100.0 at flat 85 returned an identical gap, because the
   paper had already saturated at every one of them.
3. **The blur window is not the limiter either.** `bgRadius` is
   `max(w,h)/12`, which on a 1:5 strip is wider than the strip itself and
   averages shadowed paper together with lit paper from the far side. It looks
   damning. Sweeping the radius 49 → 12 changed the gap by 3.

Two probes had to be thrown away before the numbers meant anything: one
monkeypatched `JS.flattenRGB` and measured a cached canvas, the other split the
crop setup across two `page.evaluate` calls and silently rendered the *uncropped
photo* — a 444x592 canvas where the receipt is 122x592. A probe that measures the
wrong image agrees with nothing and is worse than no probe, so both now assert
the preview's dimensions before reporting.

The estimator flaw deferred earlier is real but is *not* what the user was
looking at: `bg` is a box mean over paper and ink together, so it sits below the
paper level and the correction is driven by text density. On this fixture the
paper still lands on 255, so it does not need fixing to answer the report. It
would matter on a page where dense print covers most of a shadow.

### The yellow was a paper level, not a saturation

The report was *"auto color seems not so good as it seems to add a lot of
'yellow' to the picture"*, on a receipt photographed by a taxi's interior light.
It is not a saturation or a white-balance-matrix problem, and the fix is not
where the symptom is:

- **The colour is in the light, not in the ink.** The photo's paper is cream and
  its white reference — the brightest thing in the frame — is itself warm. A grey
  world estimate taken from the whole frame therefore calls that cream *white*
  and leaves it exactly as warm as it found it.
- **The shadow gain was making it worse.** `flattenRGB` divides out a local
  background estimated from the paper, so on a warm page the gain is derived from
  a paper level the cast has already pulled down, and the correction pushes the
  page further towards cream rather than towards white. That is why the report
  reads as "adds yellow" rather than "keeps yellow".

`JS.paperWhiteBalance` now runs first, before the flatten, and levels each
channel against the **90th percentile** of that channel — the paper — rather
than against the frame's brightest pixel, which on a shadowed receipt is a
specular highlight on the plastic, not the page. `JS.PAPER_WB_MAX = 1.55` caps
how far it may travel, so a saturated red page is corrected only as far as the
cap and a frame with no white reference at all (paper percentile under 1) is
left alone rather than being amplified into noise.

It is a **separate control from the mode**: `wb` is the *Colour strength*
slider, so the user can put it back to 0 and see the old behaviour. The sharpen
runs after it, which matters — the paper clamps as one channel, so the rails the
unsharp mask would otherwise drag out of line are already flat.

### Sharpen: the radius was the whole defect

The chip was written first and measured second, and the measurement said it
barely did anything: at step 3 on a page blurred 1.6px, total acutance gain was
**+0.37**. Two independent faults, both in the blur the mask is built from:

1. **The kernel was a fixed 3×3.** An unsharp mask can only steepen the band its
   blur reads, and a 3×3 box reads the finest one or two pixels — sensor grain
   and JPEG mosquito noise — while the smear a phone lens leaves is three or four
   pixels wide. Swept on the same blurred fixture: **radius 1 → +3.45, radius 3
   → +8.91** of acutance gain at step 3, with clipping essentially unmoved
   (45.09% → 45.6% of pixels), so the extra crispness is not bought with blown
   highlights. `JS.blurGray` was rewritten from the fixed kernel to a
   radius-taking separable sliding-window box blur.
2. **The radius did not track the render size.** `enhance` runs at
   `JS.PREVIEW_MAX` in the preview and `JS.WORK_MAX` on export, so a fixed
   radius is ~2.7× finer in *document* terms on the page that gets saved.
   Measured relative gain at 900px against 2400px: **fixed 3×3 gives +6.2% and
   +3.5%** — a ratio of 0.57, i.e. the export received 57% of the preview's
   sharpening — while `r = long edge / 450` gives **+11.2% and +11.4%**, a ratio
   of 1.02. `JS.SHARP_RADIUS_DIV = 450` is that divisor, and it is why the three
   steps now look the same in the preview and in the saved file.

Levels went from +0.37 total to **+0.76 (11.4%)** and are monotonic in `auto` and
`bw` on every fixture tried (a document, a receipt, a full-frame page, and the
AAC sample).

The **memory** choice is worth recording, because the obvious implementation is
the wrong one: an integral image of a 2400px RGB page's luminance is a 61MB
`Float64Array`, and it is rebuilt per render. Two sliding windows cost a
`Float32Array` of one channel — a window's worth — and are the same O(n).

Three properties are asserted rather than assumed:

- **The colour mask leaves the colour alone.** `JS.unsharp` adds one delta to all
  three channels, so a pixel's channel *gaps* are invariant — except where a
  channel rails at 0 or 255, which is where the measured ≤12 shift lives. The
  test counts railed and unrailed pixels separately instead of asserting the
  invariant flatly, because the flat version is false.
- **It stays local.** Paper far from any edge is untouched, which is what makes
  this a text rescue rather than a contrast bump.
- **The step counter is honest.** `JS.sharpenLevel` returns the *nearest* of
  `[mode default, 40, 70, 100]` and sends a tie to the **lower** step, so a
  slider left at 55 reads as step 1, not step 2. Four taps cycle through all
  four states and the fourth restores the mode's own value — a true undo, not a
  zero, which is what makes it stack on `auto` (whose default is 32) and on `bw`
  (whose default is 0) without either mode losing its own sharpening.

### The mode row was already overflowing at 320px

The Sharpen chip needed a place in a row that had four chips in it, so the row
was measured at 320, 360 and 390px before the label was chosen. It turned out
the row **already wrapped** — with Greyscale in it, 315.5px of 300px — and the
Sharpen chip is the *narrower* of the two (63px against 70px). A latent bug the
new chip made someone look at, not one it caused.

Fixed with `#mode-chips { gap: 3px }` and `#mode-chips .chip { padding: 3px 6px }`
→ **291.3px of 300** with the chip on its longest step; the labels are
`"Sharpen 1/2/3"` rather than `"Sharpen ×1"` because the times sign costs 8px and
the row has 8.7px of slack. It is scoped to the row rather than changed on
`.chip`, because the export sheet's three format chips have room to spare and
read better with it — and because a chip label that grows on tap and re-wraps
would move the stage under the user's finger.

> `gap: 2px` and `padding: 3px 4px`, with 12.3px of free space in the row and one
> of the labels shortened to `Colour`. The 8.7px of slack recorded above was the

### The export sheet says how big the file will be

*"in the export or share button, the default put is 90% jpg or something like
that, can we add the stimated final file size?"* The sheet had a quality slider, a
max-dimension slider, and a summary line reading `3 pages · PDF · up to 2400 px` —
three ways to change the output and no way to see what any of them did. The line
now ends in `· ≈ 1.2 MB`.

**The estimate is a real encode, not a formula.** Offered the choice, the user
took "measure a real encode" over an instant estimate. `JS.estimateExportBytes`
picks up to `JS.EST_PAGES = 3` pages spread first/middle/last across the set,
renders each at **the export's own `maxDim`**, encodes with the shipped
`JS.canvasToBlob` at the chosen quality, and scales the mean by the page count.
Nothing in that path is a model that could drift from the product, because it *is*
the product, run on a sample.

**Two cheaper designs were built, measured, and rejected.** Encoding a 600px
sample and scaling by a fitted exponent `bytes ∝ px^a` is far cheaper, and over
six pages at four qualities it was wrong by **−34% to +72%** at a 2400px export.
The reason is not a bad fit: how bytes grow with pixels depends on how much detail
a page carries, and the 600px downscale has already thrown away exactly that
detail. Per-page exponents recovered from a *second* sample ranged 0.587–0.990 and
extrapolated worse still. Weighting pages by area was also measured and also
rejected — it roughly doubles p90 and worst-case error, because a small dense
receipt strip then carries its own density across every other page's area.

So the exponent table this plan expected to bake as a constant does not exist.
Sampling at the export size costs ~30ms/page (1005px-capped photo) to ~145ms
(dense full-2400 page), which is 0.1–0.45s for three pages — affordable because
the estimate is never on the export path. `JS.buildExport` does not know it
exists.

**Three pages or fewer is not an estimate at all.** `pickSample` returns every
index when `k >= n`, so the figure shown is the number the export will produce,
to the byte. Past three it is the mean times the count. Most exports are one to
three pages, so most of the time the sheet shows an exact figure and the `≈` is
being modest.

**The PDF container is measured, not fitted.** The plan carried `242 + 455n` bytes
of overhead; the real `buildPDF` on stub pages with real dimensions and empty
image streams says nearer **239 + 462n**, and it *steps up again* when the object
numbers reach two digits, so no pair of constants holds across page counts. Rather
than model it, `JS.pdfOverhead(n, w, h)` hands `buildPDF` the real page dimensions
with empty JPEG streams and asks how big the result is. That uses the shipped
writer and so cannot disagree with it. The one inaccuracy is the digit count of
`/Length` and `startxref`, about 6 bytes per page, against estimates wrong by whole
percent. Measured across formats: 1-page PDF **−0.01%**, 1-page JPEG/PNG
**+0.00%**, 3-page PDF **−0.00%**, 4-page PDF **−1.0%**; a maxdim change of ×1.293
in the estimate against ×1.293 in the real export.

**The estimate re-runs when anything that changes it moves** — sheet open, format
chip, and the quality slider, which previously refreshed nothing at all. Two
guards on that wiring are worth naming because they are the ones that were
mutation-tested: a generation counter discards a result that arrived after the
user moved a slider again, and the debounce is ~150ms. Dropping the counter is
**caught**; making the sheet-open refresh debounced is **not**, and is recorded as
an equivalent mutant rather than papered over with a race-dependent check.

**The `Max long edge` slider is a dead control above 2400 and was left alone.**
Photos are capped at `JS.WORK_MAX = 2400` at ingest and `rectify` never upscales,
so 2500 and 4000 produce byte-identical files. The user's choice was "leave it,
show the real size" — so the estimate stops growing past 2400 by itself, because
it renders through the same cap, and the sheet tells the truth rather than the
slider doing so.

### "Done" commits a page

Done is destructive on purpose: `JS.commitPage` renders at `WORK_MAX`, replaces
`page.source` with that result, and resets rotation, crop, mode and every
adjustment. The original is released. Afterwards the page's pixels *are* the
cleaned image, so the grid, the editor and the export all show the finished
result with no special casing — and re-opening a page no longer lands the user
on the raw photo with only an outline to suggest a crop exists. Back leaves a
page unfinished; Done finishes it.

Two invariants make this safe:

- **The render runs before the reset.** Invert it and the bake re-renders the
  untouched original — the same symptom as the rotate-after-crop bug, reached
  from the opposite direction. `tests/commit_flow.js` asserts the state seen by
  `renderPage` is the finished one, and that assertion was verified to fail
  against an inverted order.
- **Committed-ness is a signature, not a flag.** `JS.stateKey` covers rotation,
  crop, mode and *every* key of `adj` (enumerated, so a slider added later
  counts by existing). `JS.isCommitted` compares against the key stored at
  commit time. No mutating code path can forget to clear a boolean — move a
  slider, rotate, re-run auto-detect, and the badge clears itself.

`original` mode still applies the manual sliders (skipping only the automatic
tone), so the controls are not dead on the page a user just finished. With
everything neutral — the post-commit state — `enhance` returns before touching
pixels at all, which is what most exports are made of.

  which is a *pass*. The filter is `getClientRects().length` plus "not inside a
  closed `<details>`", and both halves are still there because the replay page has
  a real `<details>` in it.

  This is the third version of the same trap in this suite, and the second time in
  the *opposite* direction: before 1.4.0 the drawer was a `<details>`, which
  Chromium lays out but does not paint, so the same eight sliders reported as real
  rects 300px below the fold and the no-scroll probe called every size broken when
  every size was correct. An element that is wrong while its obvious numeric
  measure says it is fine, and then an element that is fine while its obvious
  numeric measure says it is wrong. The lesson is that "visible" is not a property
  of a rect, and each new way of hiding something needs the probe re-asked.

That last one is the instructive case. The axis swap passed every *behavioural*
check — a handle drawn in the wrong place is still grabbed in the right place,
because the hit test does not read the drawing. Only sampling the drawn pixels
saw it, and the first attempt at that sample sat where the inner disc was 4.5px

The generalisation, and why the removal is tested the way it is: a test can only
catch what it actually observes. Nothing observes "this control is gone" except a
check written to look for its absence.

**Two mutations survived a full run, and both are recorded rather than fixed.**
A survivor is usually a missing guard. These two are not, and the distinction
matters enough to write down — a runner that treats every survivor as a bug
produces checks that test their own timeouts.

| Mutation | Why it survives, and why no check should catch it |
|---|---|
| the sheet-open `JS.refreshExportSummary(true)` changed to the debounced form | The debounce is 150ms and the sheet shows `measuring…` for it. The checks wait 500ms, as a person would. There is no observable difference; a check that caught this would be a check on the test's own sleep |

The first is genuinely equivalent. The second is *not* equivalent — it is a real
guard with no observable failure mode that a deterministic test can reach, which
is a different thing, and conflating the two would be how a suite acquires a
flaky check it can never delete.

## Bugs found and fixed during the build

- **Auto colour added yellow, and there was no way to rescue blurry text
  (user-reported).** *"can you add a auto sharpen button to sharpen the text?
  remove the grey scale button, and add replace it with the sharpen button. click
  and unclick to sharpen and unsharpen. sharpen is when the image is a bit blurry
  and the text is to be seen. we can add like 3 levels of sharpen. click once,
  low , click second time, med sharpen, and click 3rd time, high sharpen, and
  click forth time, undo. auto color seems not so good as it seems to add a lot
  of 'yellow' to the picture"*

  The sharpen half is a feature and the yellow half is a defect, and the defect
  was not where it read. *"Adds yellow"* is not saturation — the page's paper is
  cream and the frame's brightest pixel is warm, so the app was faithfully
  reporting a warm white as white. The gain that removes the shadow was then
  derived from a paper level the cast had already pulled down, pushing the page
  *further* cream. See **The yellow was a paper level** above.

  The sharpen half was written first and measured second, and the measurement
  found the feature did almost nothing — a fixed 3×3 kernel sharpening grain
  instead of the 3–4px smear a phone lens leaves, at a radius that was also
  wrong between preview and export. See **Sharpen: the radius was the whole
  defect**. Both faults were in the blur, not the amount, which is why the
  honest version of "it did not work" is a rewrite of `JS.blurGray` rather than
  a bigger multiplier.

  The chip's labels turned out to be a layout question: the row it went into was
  already overflowing at 320px before the chip existed. See **The mode row was
  already overflowing**.

- **Auto crop sheared the page on seven photos, and the import counter was
  invisible (user-reported, seven photos).** *"while uploading the photos, it can
  take a while. hence show a running number of progress like uploading 3 of 15
  will be good. and the auto crop is so bad - wrose than before. See photos
  set2N_be=4.jpg and setN_after.jpg, where N is 1 to 8. some are stretched
  wrongly!"*

  to the photograph's own border, and rectifying that to a rectangle is the
  shear. The lesson is the same one the earlier crop bug taught from the other
  side: the visible symptom (`stretched wrongly`) named neither the layer nor the
  cause, and only dumping the fitter's per-side buckets did.

  The seven photos are checked in as `tests/fixtures/set{21..28}_reported.jpg`
  and `ui_flow.py` runs all seven through the real `#btn-auto`, asserting the
  crop-or-decline split **and** falsifying it — the pre-guard detector is injected
  into the live page and must still crop the three that now decline. A guard that
  cannot fail is not a guard.

- **Auto crop cut through a receipt's right side (user-reported, 1.7.0).** *"the
  auto crop is so bad"* — with the photo that showed it, a taxi receipt on a dark
  surface with its own shadow beside it. The reported crop ran diagonally across
  the paper and took the amounts column with it. The cause is not ambiguity and
  not the edges: the frame-wide Otsu split landed at a level where the receipt's
  right edge and the shadow beside it are the *same tone*, so the mask's boundary
  ran down the shadow, and the fit — which is doing its job — put the right side
  there. One threshold, in the wrong place, on a frame where nothing else is
  wrong.

  The fix is a second question about the same frame (see **The paper's own
  level, as a second candidate**), and the falsifier for it is the reported photo
  itself, now checked in: the old crop's right side runs to the frame edge and
  the new one's does not. Two things about it are worth keeping. The mode-based
  candidate is only *tried* when the frame-split one succeeded, so no frame that
  was refused before can start being cropped — the change cannot make the app
  bolder on the photos it already declines. And the first version of the
  prominence test rejected every saturated paper, which is to say every white
  receipt in daylight, because it clamped the right shoulder into the top
  histogram bin where the shoulder *is* the peak; `pair1` reported a 4.3%-mass
  midtone peak at 121 as its paper level while the paper sat at 249. Guarding a
  new path found a defect in the new path, which is the argument for guarding it.

- **Auto crop invented tilts on upright photos (user-reported, four photos).**
  *"i am giivng you 4 pairs of wrong autocrop. see pictures pairX_b4.jpg and

  for the diagnosis — the score curve on those frames has no alignment peak in it
  at all, and the guard now refuses a curve whose own minimum is more than a
  quarter of its height.

  Two things about the fix are worth keeping. The four photos were **recovered
  from the screenshots** (`tests/tmp/make_deskew_fixtures.py` cuts the photo back
  out of the editor's black letterbox) and are checked in under
  `tests/fixtures/`, so the report is a regression test rather than a story. And
  the *cost* is deliberate and stated: Auto crop now straightens **much less
  often**, because on real photographs the projector's peak is broad. A page left
  slightly tilted is recoverable — the fine slider, or the corners that came back

  `JS.undoAll` replaced `JS.resetCrop` (and `#btn-reset-crop` became
  `#btn-undo-all`): the old button cleared the crop and the fine angle, the new

- **A mode chip could be lit and not put back (user-reported, 1.5.0).** *"when i

- **Cleaning broke thin or blurry words (user-reported, 1.5.0).** *"auto clean

- **Auto-crop came back with the text block instead of the page (user-reported).**
  The user's photograph was already upright and filled the frame side to side,
  so the only edge in it was the one at the bottom where the paper ended and the

  table's margins — slicing the first letters off `ATHLAB` and `CLIENT ID`.

  `boundaryPixels` was returning every page pixel with a non-page neighbour,
  which includes the rim of every *hole*, and a page of text is mostly holes.
  The printing contributed 2754 points against the outline's 1200, and the fits
  followed the printing. See *Boundary points are the sheet's outline* above for
  the fix.

  Three layers of diagnosis, none of them by reading the code and guessing:
  the photo region was cut out of the user's screenshot, the real detector was
  run over it in Chromium and dumped, and then the module's private helpers were
  re-evaluated in the page with `__dbg` hung off `JS` so each refinement pass
  could report its own buckets, cores, residuals and fitted lines. The four
  fitted sides at `y≈23.4, x≈193.7, y≈307.6, x≈35.7` *were* the table's box —
  that is what identified it, not a hypothesis about the code.

  **The coverage failure is again the more important half.** Nothing pressed
  the detector: `ui_flow.py` set `p.corners` by hand in every section. A browser
  section now presses it, and `smoke.js` counts the boundary points — but the
  browser section alone would not have caught this, which is why the count is
  taken where the decision is made. That is the same lesson as the rotate bug
  from the opposite direction: there, the maths was right and the button was not
  wired; here, the button was wired and the layer *above* everything under test
  was wrong.

  Scratch tooling for the diagnosis lived in `tests/tmp/` (`repro.py`,

- **The page at a quarter of the screen and the buttons below the fold
  (user-reported).** *"the image should occupy half of the page. now it is like
  1/4 only on my mobile. and, the buttons are to be made smaller - i do not have

  the panel leaves* above for the diagnosis and the fix.

  every rule did what it said. What was missing was any check that could see it.
  `ui_flow.py` asserted the layout with `page.is_visible("#btn-auto")`, and
  `is_visible` means "has a non-empty box" — it is true of a button 400px below

  Measured numbers, since they are the whole point: the page went from 29.2% of

  Scratch tooling for this round: `layout_probe.py` (the four-size

- **"i do not want to have to scroll up and down" (user-reported, follow-up).**
  The previous fix pinned the buttons in the footer and left the panel scrollable
  under a `min(26vh, 210px)` cap. That satisfied the literal complaint — Done no
  longer moved — but not the request: the panel still scrolled at every phone
  size, by 233px at 375×667, and the crop controls were a flick away. The user
  asked for the picture and every control on one screen.

  The fix inverts the layout relationship. The panel is content-sized and the
  stage takes the remainder, so extra height costs the page rather than hiding a
  control; the panel's `overflow-y` and cap survive only as a short-screen safety
  valve. Content came down from 406px to 222px via `--tap` 40 → 34, the crop
  group's three rows to one, `Reset tone` into the drawer with its own sliders,
  and the crop hint deleted (its content is in Help, and the stage hint says the
  same thing contextually).

  Two traps in this round, both again in the measuring rather than the layout:

  - **A closed `<details>` is laid out but not painted in Chromium.** Its subtree
    reports ordinary, non-zero bounding rects — 300px below the panel — and
    contributes nothing to `scrollHeight`. My first no-scroll probe therefore
    flagged all sixteen configurations as broken, including eight that were
    correct. It is the same family of error as the clipping-vs-rect one above: a
    rect answers "where would this be", not "is this on screen". The checks now
    skip anything inside a closed `<details>`.
  - **`flex-shrink` on two content-sized siblings splits the shortfall.** With
    both at the default 1, a column 5px short took 5px off *both* — and 5px off
    the panel is 5px of scroll, which is the defect. At 360×640 that was exactly
    what the measurement showed. `flex-shrink: 100` on the stage against the
    panel's 1 makes the stage give way first, all the way to its floor.

  Measured: panel scroll **0px** at 320×568, 375×667, 360×740, 390×844, 430×932,
  with every visible control inside the panel's box and inside the screen, and
  the page at 35.1 / 44.8 / 50.3 / 56.4 / 63.5%. The trade is explicit in the
  suite: the old arrangement kept the page at 47.8% *by* scrolling, and a check
  in the replay asserts that 47% so it does not get quietly forgotten.

  Scratch tooling: `budget_probe.py` (per-row heights against five viewports,
  which is what made the 406 → 222 accounting possible), `noscroll_probe.py`
  (the eight-size sweep with the drawer open and closed, and the one that had the
  `<details>` bug), `shot.py` + `shot_*.png`.

- **The crop that was the hand, and the tilt that was never measured
  (user-reported).** Two independent defects, both found by measuring the user's
  own photo rather than reasoning about the code. See *A background is a border
  that is decisive and one material* above.

  The mean-vs-threshold guard was written first, passed its own falsifier, and
  **broke two checks in the existing suite** — a bright sheet on a uniform dark
  field legitimately has a margin of 0. The suite caught it in one run, before
  the wrong guard reached a commit; that is the whole argument for having
  fixture-based checks rather than prose. The replacement was chosen from a
  measurement (`tests/tmp/border_stats.py`, `border_photos.py`) that printed
  margin *and* border spread for every fixture, good and bad, at once — the same
  discipline as the shadow work: the statistic that separates the cases is
  usually not the one that seemed obvious.

  Scratch tooling for this round: `polarity_scene.py`, `skew_scene.py`,
  `skew_width.py`, `border_stats.py`, `border_photos.py`, `mixed_falsify.py`,
  `skew_probe.py`, `skew_loop.py`, `skew_calib.py`, `diagnose.py`, plus
  `real_photo.jpg` — the user's photo, cut out of their screenshot and used to
  reproduce the report. `tests/tmp/` is gitignored scratch space; the *durable*
  fixtures are all generated by the tests themselves, so nothing in the repo
  depends on a binary.

- **Rotate turned the state and not the picture (user-reported).**
  `rotateCoarse` moved each corner and left the list order alone. That is a
  cyclic shift by one, and `rectify` reads its output width from the length of
  edge `(q0,q1)` and its height from `(q0,q3)` — which is only true while index 0
  is the top-left. So the two edges swapped roles and every rotated page came out
  transposed: `coarse` went 0 → 90, the content turned inside the frame, and the
  frame did not turn with it, so the stage looked identical. Measured through the
  browser test: aspect **0.750 → 0.751** for a page that should have gone to
  1.333.

  It had a second cost: `rectify`'s `isPlain` fast path tests for a corner at
  (0,0), which a shifted quad does not have, so a plain quarter turn left the
  cheap path and paid for the whole per-pixel homography.

  Fixed by re-indexing as well as rotating — the offset is 3 for a clockwise turn
  and 1 for anticlockwise, since those are the old corners the turn carries onto
  the new top-left. Both directions are checked, so the offset is not tuned for
  one of them.

  **The coverage failure is the more important half.** No test pressed the rotate
  button. `smoke.js` exercised the corner algebra and `oriented_render.py`
  exercised the canvas composition, and both were green while the button did
  nothing — and worse, an existing check asserted `corners[0]` still held the
  rotated old corner 0, which *pinned the bug as if it were the contract*. A test
  written from the implementation rather than from the requirement will happily
  defend the defect. Both suites now assert the canonical ordering, the frame
  swap and the content tracking, and all five checks fail against the pre-fix
  code.

- **Every pointer on the crop inset was a pixel off** *(the inset is since
  removed, and the crop handles that replaced it are a different surface — but
  the lesson is kept, because it is about how the check was written)*.
  `pointerBoxPos` mapped `clientX/clientY` through
  `getBoundingClientRect()`, which returns the **border box**, while the canvases
  it was drawing into and the box `insetBox()` measured with
  `clientWidth`/`clientHeight` are the **padding box**. The 1px border therefore
  shifted every grab. Found by the ui_flow check that compares the crop
  surface's rect against its parent's — which was itself written wrong (it also
  used the border box) and only disagreed by exactly the border width, which is
  what gave it away. Fixed with `- el.clientLeft` / `- el.clientTop`.

  The lesson is in the test, not the app: the drag check derived its expected
  cursor position from `#src-inset`'s border box and was off by the same pixel,
  showing a residual of 0.00324 (~1.2px) that read as float noise. Deriving it
  instead from the surface that actually receives the pointer — a DOM fact, not
  app code — dropped it to 0.00104 (0.39px, Chromium's integer `clientX`
  rounding). Two independent derivations agreeing to the pixel is what turned a
  "tolerance" into a diagnosis.

- **A UI removal leaves its state and helpers behind.** Removing the crop inset,
  hold-to-compare and the inset's corner drag was a deletion across five files.
  The things that could silently survive are not DOM nodes — a stale
  `app.comparing` key, an exported `JS.drawInset`, a `CACHE_SLOTS` justified by a
  drag that no longer happens, a comment describing a surface that is gone.
  `ui_flow.py` now asserts the absences directly, and the removal was
  mutation-tested by re-introducing `JS.normToBox` (caught).

  The corner drag itself came back later on a different surface — the handles now
  ride the preview's own box, which is not the inset — so a stale `normToBox` and
  a new `cropMapper` coexist in the tests only in the sense that one is pinned
  absent and the other exercised. The `CACHE_SLOTS = 3` survives for the slider
  drag (below), not for a corner.

- **A corner drag rebuilt the canvas it was about to draw from.** Per-page
  derived-canvas cache was two slots, and three sizes are genuinely live while a
  slider is being dragged (fast preview, full preview, grid thumbnail), so the
  smallest was always the one evicted and paid a full re-warp each time round.
  `CACHE_SLOTS` is now 3.

- **Rotating after a crop threw the crop away (user-reported).** `orientedCanvas`
  drew the source into the *swapped* canvas dimensions:
  `drawImage(src, -w/2, -h/2, w, h)` where `w`/`h` were the oriented canvas
  size. For a 1000x2000 photo at 90° that stretched the page to 2:1 *before*
  rotating it, so the content ended up 450 wide in a 900-wide canvas — clipped
  top and bottom, with empty bands left and right. The user saw a narrow strip
  and reasonably concluded the rotation had ignored the cropped image.
  Fixed by extracting `JS.orientedLayout`, which gives the canvas the rotated
  dimensions but draws the source at `page.w * s` x `page.h * s`, keeping its
  own aspect ratio.

  Two things made this worth a dedicated test rather than a one-line patch:
  the corner algebra (`rotateCoarse`) was already correct, so the fault was
  purely in the draw rect; and a square photo hides it completely, because
  swapping equal dimensions is a no-op. `tests/oriented_render.py` now rasterises
  the composition and checks the border and a marker's landing position at all
  four angles, and `orientedLayout` is exercised as pure maths in `smoke.js`.

- **Every `hidden` toggle in the app was dead.** The JS hides panels, sheets and
  the busy overlay by setting the `hidden` attribute. The UA rule for that is
  `[hidden] { display: none }`, but *author* styles beat UA styles regardless of
  specificity, so `.sheet { display: flex }`, `.busy { display: flex }`,
  `.page-grid { display: grid }` and `.btn { display: inline-flex }` all
  overrode it. Symptom the user hit: the help sheet's "Got it" button did
  nothing. Same root cause meant the busy spinner could never be dismissed and
  the empty state never went away. Fixed with a global
  `[hidden] { display: none !important }`; `tests/dom_check.js` now asserts the
  rule exists and reports which classes depend on it. Note this class of bug is
  invisible to the node tests — it needs a browser, or the CSS lint that was
  added afterwards.

- **Adaptive threshold washed out large dark areas.** Bradley–Roth whitens the
  interior of any dark region wider than its window (filled logos, barcodes,
  heavy rules). Added an absolute floor. Covered by a test that asserts both
  the artefact and the fix.
- **Otsu boundary convention.** Otsu returns the *last bin of the dark class*,
  so the comparison must be `v <= t` for dark. The original `<` misclassified
  perfectly bimodal images; it also affected page detection and ink counting.
- **Deskew sign.** The projection-profile loop rotated by `-ang` while the
  derivation assumed `+ang`, which would have doubled the tilt instead of
  cancelling it. Caught by a synthetic-tilt test.
- **`#btn-save` ("Done") was never wired** — tapping it did nothing. Found by
  the DOM check.
- **Memory blow-up.** Storing per-page canvases at 2400px is ~17 MB each, so a
  dozen pages kills a phone tab. Moved to blob-backed `<img>` sources,
  normalised corners, and bounded caches.
- **PDF xref offsets.** Two *test* bugs (`lastIndexOf('xref')` matching inside
  `startxref`; a `\r`-intolerant regex) were masking correct output.

## Known limits

- **A pale page on a pale surface is refused, and the reason is the ink, not the
  tone.** The user's second reported crop failure, in their words: *"sometimes it
  is bec the background is a little similar colour tone as the document"*. It is
  a real limit and it is **not the mechanism they described**, which is why this
  entry exists rather than a code change. Measured by `tests/tmp/pale_probe.py`
  on a synthetic frame (paper 248 on a counter 236, with a shadow gradient and
  noise) at a known quad:

  | | margin | delta | thr | page−bg | mask | verdict |
  |---|---|---|---|---|---|---|
  | 248 on 236, printed | 88.1 | 30.8 | 138 | 20.5 | 0.052 | **refused, 684** |
  | the same, no ink | 10.9 | 16.0 | 237 | 21.9 | 0.488 | found |

  The obvious hypothesis — that `delta = Math.max(16, …)` is a 16-level floor
  bigger than the whole scene's contrast, so no pixel is ever called paper — is
  **false here**: `delta` is 30.8 and the border reference is 88.1 away from the
  split, so the border guard (668) never fires. What actually happens is that
  Otsu splits at **138**, which is between the ink (around 40) and the paper
  (248) rather than between the paper and the counter. The mask therefore selects
  the *printing*, not the sheet, and the refusal is 684: the mask is text
  fragments, not one page-shaped blob. Take the ink out and the same frame is
  found at mask 0.488 with `thr` 237.

  Consequences, all measured rather than argued:

  - It is refused at **every** ink density from 9/10 cells down to 1/10, moving
    from 684 to 681 as the printing thins.
  - A **4× contrast stretch about the border level does not rescue it** — the ink
    stretches with the paper, so the split stays between them. (It is also why
    the no-ink controls report `x4: NO`: the stretch saturates and takes the
    split with it.)
  - The fix the plan proposed — normalising the detection grayscale with
    `JS.flattenBackground` before classifying — **would not work**, because the
    separation between page and background was never what failed.

  **The four real fixtures that decline are a different mechanism again.** All 11
  were run through their own pipeline path: `pair3`, `set21`, `set23` and `set27`
  refuse at **689–693** (edge fitting, then area), not at any of the tone guards,
  and their statistics are indistinguishable from the ones that are accepted —
  `set23` is declined at a blob fraction of **0.749** while `set22` is accepted at
  **0.748**. No tone-side change would touch them either.

  So nothing ships for this beyond the measurement, which is what the plan said
  would happen if the guardrails could not be met. **The eight crop handles are
  the remedy**: a refusal that asks for a manual crop is a better failure than a
  wrong crop, and the two mechanisms above are not one bug. What *would* fix the
  synthetic case is a second split *within* the light class — paper against
  counter, once the ink is excluded — and that is a detector change with no
  evidence yet that it helps the four real declines, which are the ones a user
  actually hits.

- **The shipped stage share at 320×568 is 69.95%, and the record carries it both
  as 69.9% and as 70.0%.** The stage is 397.328125px of 568. `stage_frac.py` and
  `ui_flow` round the height first (397 / 568 = 69.89% → "69.9%"); the chip-row
  probes round the fraction (69.95% → "70.0%"). Both are correct, the gap is
  0.3px, and it is written down here so that nobody sets out to find which probe
  is lying. All three now open the editor on a fresh 2× page so they cannot drift
  further apart.

- **The panel is two lines at 65px, and neither line has slack in it.** The page
  is 74.4% of a 375×667 screen and nothing scrolls; the cost is now width rather
  than height. The tone row at 320px carries *Colour* / *Receipt* / *Sharpen 3* /
  *B/W* / *Custom*, with **12.3px free**, and the crop row's three buttons leave
  the fine-angle slider 68px — the floor for a ±15° control, and the reason the
  rotate buttons have no glyphs. A longer chip label needs the row measured rather
  than looked at, and `rowFit`'s `subWrap` is the field that says so — it did not
  exist when the Receipt chip was added back, and the wrap it missed cost the
  stage 27.6px with every check still green.
- **The four footer buttons fill their row too**: at 320px each is 72px and
  *Auto clean* wants 62px, with `.btn` at `white-space: nowrap` so a fifth button
  would paint over its neighbour rather than wrap. That is what moving the pager
  to the topbar bought.
- **The Custom drawer is the one thing behind a tap**, and opening it is the only
  thing that scrolls the panel. Eight sliders plus *Reset tone* are ~340px and
  cannot be shown with the page on any phone.
- **The panel's order is still load-bearing** — the tone row above the crop row,
  because Auto clean acts on the mode — even though nothing is under a fold. It is
  now also the reading order. Reordering the rows is caught by a test, because it
  is a behaviour, not a preference.
- **The preview's zoom is a view, not state.** It is not saved with the page, not
  part of `stateKey`, and not part of what makes a page "edited": pinching to read
  a corner and then tapping *Done* bakes exactly what it would have without the
  pinch. It springs back to fit when the page changes, and `setView` clears it on
  the way out of the editor.
- **The pan clamp is the loose one, deliberately.** The image's centre may sit
  anywhere inside the box it was fitted in, so just above fit zoom there is a
  strip of empty stage — worst case 74.9% page against the 72% the fitted view
  shows. The tighter cover-the-box rule is what a photo viewer uses and it is what
  the corner grab cannot survive: it would move a grabbed corner 43.5px across and
  11px down, out from under the finger.

- **Done is not undoable**, by design — the user asked for the original to be
  forgotten. The file in the phone's gallery is never touched, so the raw photo
  is still recoverable from there by re-adding it.

- Detection needs the page to contrast with its background. White-on-white
  fails by design (reports "no clear page edge") rather than guessing.
- A page edge needs a *seam*: the paper's own shadow on the surface below it, a
  tone difference, a fold. Where the floor right under the sheet is as bright as
  the sheet itself there is no boundary in the image at all, and the crop runs
  past the paper to wherever the two do part. The synthetic full-frame fixture
  needed that shadow added to be detectable, which is what surfaced the limit —
  it is a property of looking at one photograph, not a tuning problem.
- **The manual crop is eight drags — four corners and four side midpoints — and a
  handle cannot be dragged onto the line between its two neighbours.** That is
  the convexity limit, and it is what refuses a folded or bowtie quad (which
  would invert the homography and render garbage) — but it also means the
  *middle* of the page is unreachable by dragging a corner inward, because the
  fold line passes exactly through it. The drag stops there rather than jumping.
  Every other target inside the page is reachable, and the four corners between
  them cover any rectangle that fits inside the photo. The side handles move two
  corners as one, but they are still bounded by that same line, so a side cannot
  be pushed past its neighbours either.
- **A crop cannot add back what a previous crop removed.** Once a page is
  committed, the pixels outside the crop are released — Undo all restores the
  *state*, not the discarded image, so it is only complete until Done. Before
  Done it is complete, which is when it is meant to be used.
- **Shadow removal is a flatten, not a shadow detector.** It estimates the paper
  level locally and lifts everything towards it, which is why `flat` is a blend
  rather than a switch and why a hard-edged cast shadow across the page can
  survive it as a soft grey. The receipts it was tuned on leave a gap of 0
  between the two halves; a shadow stronger than the ones in the fixtures has no
  guaranteed headroom left. `Black & white` is the mode that will always remove
  one, because the threshold discards mid-greys entirely.
- **The detector treats a shadow's edge as the page's edge.** On a strongly
  shadowed sheet it can take the *lit* part as the page and crop the shadow away
  — which removes the shadow by cropping it, and is why the shadow report could
  not be reproduced from a fixture: there was nothing left inside the crop to
  differ about. Whether that is the right call is a separate question from the
  flatten's strength.
- **Sharpen cannot invent detail, and its steps narrow as they climb.** It
  steepens the edge the lens left, so a photo blurred past the point where a
  stroke still has an edge comes back with firmer smudges rather than legible
  ones — the honest description of the three steps is *more* and *most*, not
  three times the first. The mask clamps, which is why step 3 is not 3× step 1,
  and why the gain is measured (11.4% at the top) rather than asserted.
- **Sharpening makes the B&W threshold's false ink line more visible.** A soft
  shadow edge that the adaptive threshold draws a line along is steeper after
  the mask runs, so the line is crisper and raggeder. It is **there with the
  sharpen off** — this sharpens an existing artifact rather than creating one —
  and net ink still *falls* as you sharpen (0.18% of the page at step 1 to 0.45%
  at step 3), because thinning blur-fattened strokes back toward their true
  width is what sharpening a thresholded page does. Stated because it is the one
  place the control can make a page look worse.
- **The white balance needs a white reference to find.** It levels against the
  paper's own 90th percentile, so a page whose brightest paper is genuinely grey
  — or a frame with no page in it at all — has nothing to level against, and a
  frame under a paper percentile of 1 is left alone rather than being amplified
  into noise. A page lit by a strongly coloured light is moved towards neutral
  only as far as `JS.PAPER_WB_MAX = 1.55` allows, which is deliberate: past that
  the correction starts recolouring the ink.
- **A curled or torn corner is not found, and this build does not claim to find
  one.** Corner settling was built and dropped (see *Corner settling was built,
  measured, and dropped*); the acceptance test cannot see a corner at all,
  because it samples 15%–85% along each side. A paper whose corner is folded over
  or lifted off the surface gets a quad through the middle of the fold, and the
  eight crop dots are the remedy. **`Set30` is the reported case and it is still
  unmeasured**: the only copy to hand is a screenshot of the *result*, and a
  source rebuilt from it detects cleanly with every corner above 0.94 of paper.
  The original photo is needed before anything can be said about it — including
  whether the corner or the edge was the fault, which was got wrong once already
  in this work (the screenshot's edges measure fine; its top-right corner is 86%
  background).
- Clean modes are heuristic, not per-document adaptive.
- Deskew searches the slider's own ±15° at both stages, and refuses rather than
  clips: an angle at the scan's edge, or a score curve with no collapse in it,
  comes back 0. Auto crop therefore straightens less often than it used to — see
  **Tilt**.
- No persistence — export before closing the tab. A before-unload prompt warns.
